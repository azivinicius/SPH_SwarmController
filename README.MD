# SPH_Project — CrazySim + Crazyswarm2, custom multi-drone controller

A from-scratch ROS2 package (`drone_controller`) built and tested step-by-step
against CrazySim (Gazebo) + Crazyswarm2, running entirely inside one Docker
container. The project has two tracks that share the same underlying SPH
physics: an **offline, pure-Python tuning loop** (CMA-ES over the SPH
parameters, no Gazebo needed) and the **in-the-loop ROS2 controller** that
flies the simulated drones. On top of the SPH forces, the in-the-loop
controller adds an **external potential** that pulls the swarm onto a circle.

There are **two ways to run the simulation**: a one-command tmux launcher
driven by a config file (see [Running with tmux](#running-with-tmux-recommended)),
and the original three-terminal manual procedure (see
[Running manually](#running-manually-without-tmux)). Both are kept up to date.
This doc is the running reference for how to build it, run it, and the real
gotchas already hit along the way — update it as things change.

## Hardware / OS notes

- Native Ubuntu 24.04 (not WSL2, not macOS).
- Dual-GPU laptop: Intel UHD 620 (integrated) + NVIDIA GeForce MX110 (discrete).
  **Intel is the active rendering path, deliberately** — it was already working,
  is more than adequate for Gazebo Garden, and this machine's NVIDIA driver
  stack has been independently flaky. `docker-compose.yaml` reflects this:
  `gpus: all` stays commented out; the `/dev/dri` device passthrough is what's
  actually used.

```
            ├── controller.py      # read-only SPH diagnostics node — BROKEN, see Known issue #6
```

`config/` and `src/` are bind-mounted into the `crazysim` container (see
`docker-compose.yaml`). Editing files on the host takes effect immediately —
`config/` changes need a Gazebo/Crazyswarm2 restart, `src/` changes need a
`colcon build` inside the container (except `raw_sim.py`/`CMA_ES.py`, which
don't need ROS or a build at all — see Track A below).

## First-time setup

```bash
cd ~/SPH_Project
docker compose build crazysim   # ~10-20 min: compiles SITL firmware + colcon-builds crazyswarm2_ws
```

For the tmux launcher, also install tmux on the **host** (the scripts need
nothing else beyond `python3`, which is already there):
```bash
sudo apt install tmux
chmod +x dev_tmux.sh gen_config.py
```

## Running with tmux (recommended)

One host terminal, one command. `dev_tmux.sh` starts the container, generates
the drone configs, and opens a tmux session with four windows. Every command
inside runs in the `crazysim` container via `docker compose exec`.

```bash
cd ~/SPH_Project          # must run from here: the script uses relative paths
./dev_tmux.sh show        # print the resolved config + launch args, start nothing
./dev_tmux.sh up          # generate configs, start everything, attach
./dev_tmux.sh attach      # re-attach to a running session
./dev_tmux.sh stop        # stop everything (see below)
```

| Window | Runs |
|---|---|
| `sim` | Gazebo + SITL firmware (headless) |
| `swarm` | Crazyswarm2 (`ros2 launch crazyflie launch.py`), after `SIM_WAIT` seconds |
| `ctrl` | `colcon build`, `source src/dev_setup.bash`, `plain_sph.launch.py` with every arg from `swarm.conf`, after `SIM_WAIT + SWARM_WAIT` seconds |
| `shell` | `/all/takeoff` after `SIM_WAIT + SWARM_WAIT + TAKEOFF_WAIT` seconds (if `AUTO_TAKEOFF=1`); otherwise a free window |

### Configuring a run: `swarm.conf`

All knobs live in `swarm.conf` (shell syntax, `KEY=${KEY:-default}`), so any of
them can also be overridden for a single run from the command line:
```bash
N_DRONES=5 POT_R=0.8 ./dev_tmux.sh up        # one-off overrides
CONF=configs/five.conf ./dev_tmux.sh up      # use a different config file
```

| Key | Default | Meaning |
|---|---|---|
| `N_DRONES` | `3` | number of drones |
| `SPAWN_RADIUS` | `0.5` | drones spawn evenly spaced on a circle of this radius around (0,0) |
| `POT_XC`, `POT_YC` | `2.0`, `2.0` | centre of the target circle |
| `POT_R` | `0.5` | radius of the target circle |
| `POT_K`, `POT_BETA` | `2.0`, `1.0` | potential force gain (`f_k`) and exponent (`f_beta`) |
| `SPH_MASS`, `SPH_H`, `SPH_RHO0` | `7000.0`, `3.0`, `1000.0` | particle mass, smoothing length, rest density |
| `SPH_GAMMA`, `SPH_ALPHA`, `SPH_BETA`, `SPH_ZETTA` | `7.0`, `1.0`, `2.0`, `30.0` | EOS exponent, viscosity coefficients, extra damping (`zetta_extra`) |
| `FIXED_Z`, `TAKEOFF_HEIGHT` | `0.5`, `0.5` | see note under "Control path" in Track B |
| `AUTO_TAKEOFF` | `1` | `1` = call `/all/takeoff` automatically |
| `RVIZ` | `True` | `True`/`False`, passed to the Crazyswarm2 launch |
| `SIM_WAIT`, `SWARM_WAIT`, `TAKEOFF_WAIT` | `15`, `15`, `20` | startup delays in seconds |

**The delays are estimates, not measured.** If Crazyswarm2 starts before Gazebo
is ready, or takeoff fires before `/cf_N/state` exists, raise them
(`SIM_WAIT=25 SWARM_WAIT=25 ./dev_tmux.sh up`) or set `AUTO_TAKEOFF=0` and call
takeoff by hand from the `shell` window. Whether takeoff should come before or
after the controller starts has not been confirmed — tune `TAKEOFF_WAIT` from
what you observe.

**`up` rewrites the drone config every time.** Before starting anything,
`gen_config.py` regenerates `config/agents.txt` and the `robots:` block of
`config/crazyflies.yaml` (everything else in the yaml is preserved), with
drones evenly spaced on a circle of `SPAWN_RADIUS`. Hand-edited spawn
positions are overwritten. It prints the resulting neighbour spacing and warns
below 0.3 m. Changes only take effect on a fresh start — run `stop` first if a
session is already running.

### Stopping

- **Inside tmux, from any window:** press `Ctrl+b` then `K`. The status bar
  shows this reminder.
- **From any terminal:** `./dev_tmux.sh stop`.

Both do the same thing, in this order: send Ctrl+C to the controller (so
`plain_sph` flushes its CSVs), wait 3 s, kill the leftover processes inside the
container (`plain_sph`, `ros2 launch`, Gazebo, `cf2`, `ruby`), `chown` the logs
to your host user (done inside the container as root — no `sudo`), and kill the
tmux session **last**. Killing the session last matters: when `stop` runs from
inside tmux, killing the session kills the script itself.

To leave everything running and come back later, detach with `Ctrl+b` then `d`
and use `./dev_tmux.sh attach`.

### tmux cheat sheet

- `Ctrl+b` then `0`–`3`: jump to window (`sim`, `swarm`, `ctrl`, `shell`).
- `Ctrl+b` then `n` / `p`: next / previous window.
- `Ctrl+b` then `[`: scroll back (`q` to leave).
- `Ctrl+b` then `d`: detach, leave everything running.
- `Ctrl+b` then `K`: stop everything.

**Avoid** `tmux kill-session` / `tmux kill-server` on their own: they only drop
the `docker exec` clients, and the processes inside the container can keep
running. `kill-server` also ends unrelated tmux sessions.

After a run, leftover-process check:
```bash
docker compose exec crazysim ps aux | grep -E 'gz|cf2|ruby|ros2'
```

## Running manually (without tmux)

This is the original three-terminal procedure and still works as-is. Use it if
you want to watch each process separately or if the tmux launcher misbehaves.

`root@...` = inside the container (correct for all `ros2`/`colcon` commands).
Your own host username = wrong terminal — see Known issue #4. Always check
your prompt.

**After every PC restart, do this first** (the container does not
auto-start on boot — see Known issue #9):
```bash
cd ~/SPH_Project
docker compose up -d crazysim
xhost +local:root
```
Only after this succeeds will `docker compose exec -it crazysim bash` work.
If you skip it, `exec` fails immediately with `service "crazysim" is not
running` — that message means exactly what it says, not a Docker/config
problem.

**Drone count / spawn positions.** `config/agents.txt` and
`config/crazyflies.yaml` must stay in sync (see "Multi-drone config"). Either
edit both by hand, or generate them on the **host**:
```bash
cd ~/SPH_Project
python3 gen_config.py --n 5 --radius 0.5
```
Restart Gazebo/Crazyswarm2 afterwards so they re-read the files.

**Terminal 1 — Gazebo + SITL firmware (headless, default):**
```bash
docker compose exec -it crazysim bash
cd /CrazySim/crazyflie-firmware
bash tools/crazyflie-simulation/simulator_files/gazebo/launch/sitl_multiagent_headless.sh -f agents.txt
```
No GUI window opens — this is deliberate. Physics and firmware behave
identically either way; you just don't get a 3D view. See Known issue #7 if
you want the GUI instead.

**Terminal 2 — Crazyswarm2:**
```bash
docker compose exec -it crazysim bash
source /CrazySim/crazyswarm2_ws/install/setup.bash
ros2 launch crazyflie launch.py backend:=cflib rviz:=True
```

**Terminal 3 — your controller** (note: `src/dev_setup.bash`, NOT plain
`install/setup.bash` — see Known issue #1):
```bash
docker compose exec -it crazysim bash
cd /root/dev_ws
colcon build --symlink-install
source src/dev_setup.bash

# one drone by hand, simple P-controller to a fixed target:
ros2 run drone_controller hello_node --ros-args -p robot_name:=cf_0 -p target:="[0.8, 0.0, 0.5]"

# several drones with the same node:
ros2 launch drone_controller controller.launch.py

# the actual SPH swarm controller (see Track B below), defaults:
ros2 launch drone_controller plain_sph.launch.py total_robots:=3

# same, overriding any launch arg (full list in Track B):
ros2 launch drone_controller plain_sph.launch.py total_robots:=5 R:=0.8 f_k:=3.0
```

**Takeoff.** `plain_sph` only streams velocity commands, so the drones need to
be airborne:
```bash
ros2 service call /all/takeoff crazyflie_interfaces/srv/Takeoff "{height: 0.5, duration: {sec: 2, nanosec: 0}}"
```
(The tmux launcher does this for you after a delay. The order relative to
launching the controller hasn't been confirmed; see the note under "Running
with tmux".)

**Stopping, manually.** Ctrl+C the controller terminal **first** (that is what
flushes the CSVs), then Ctrl+C the Crazyswarm2 and Gazebo terminals. Then, on
the host, fix log ownership before plotting:
```bash
sudo chown -R $USER:$USER ~/SPH_Project/src/logs
```


## Two tracks: offline SPH tuning vs. flying it for real

Both tracks implement the same 2D SPH swarm model (based on Pimenta et al.
2013, "Swarm Coordination Based on Smoothed Particle Hydrodynamics
Technique"), but live in very different environments. **The whole stack is 2D**
— `Particle` has no z, `Potential` is a circle in x–y, and the controller
commands zero climb rate. A 3D variant would need a 3D particle/kernel, a
sphere potential, and a vertical velocity command; none exist yet.

### Track A — Offline tuning (pure Python, no ROS2, no Gazebo)

Files: `particle.py`, `raw_sim.py`, `CMA_ES.py`.

This is where `gamma`, `alpha`, `beta`, and `zetta_extra` (the equation-of-state
exponent and artificial-viscosity coefficients) actually get tuned. It's a
self-contained SPH simulation of an n×n grid of particles — only needs numpy
+ matplotlib, no ROS/Gazebo dependency at all. Because it's fast and
self-contained, this is what `CMA_ES.py` calls internally, hundreds of times,
to score each candidate parameter set during the search.

Run a single simulation with a given parameter set (works outside the
container too, on any machine with numpy + matplotlib):
```bash
cd src/drone_controller/drone_controller
python3 raw_sim.py --gamma 0.0457 --alpha 0.6419 --beta -0.2906 --zetta_extra 0.2905
```
Flags: `--headless` skips the animation window (prints a summary + still shows
the history plots); `--no-history` skips those too. Run `--help` for the full
list (`--n`, `--mass`, `--h`, `--rho_0`, `--dt`, `--num_steps`,
`--expected_distance`).

Run the full CMA-ES search:
```bash
python3 CMA_ES.py
```
Took **~3 hours** on this hardware for 100 generations at the current
settings (8×8 grid, 200 steps per candidate) — there's no interruption/resume
built in yet, so budget the time before starting. Prints per-candidate status
(cost, `ok`/`divergiu`/`parametros invalidos`, timing) and per-generation
summaries as it goes, then shows a 4-panel diagnostic dashboard (cost
convergence, sigma, parameter evolution, covariance condition number) and a
breakdown of the final cost by term.

`h` and `mass` are **not** free parameters here — they're derived
analytically from the drone's sensing radius and target inter-drone spacing
via the SPH kernel-support and equilibrium-density equations (`h =
sensing_radius / 2`; `mass` solved so that `rho(target_spacing) = rho_0`).
Current values, for a 1.5 m sensing radius and 0.5 m target spacing:
`h=0.75`, `mass=795.2156`, `rho_0=1000.0`.

**Current result and a known caveat:** the last full run converged to
`gamma=0.0457, alpha=0.6419, beta=-0.2906, zetta_extra=0.2905` (cost
64.29). Replaying that exact parameter set confirms real convergence — the
closest-neighbor spacing tightened from the 1.0 m initial grid down to
**~0.62 m**, not exactly the 0.5 m target — while the farthest pair stayed
pinned at the original **1.0 m**, almost certainly the grid's outer/corner
particles (fewer neighbors pulling them inward — a standard SPH free-surface
effect, not obviously a tuning failure). No collision risk (spacing never
dropped below target) and the swarm stays well inside the 1.5 m sensing
radius, but it's not a perfectly uniform lattice. Worth another pass with a
higher `spacing_ceiling`/`spacing_floor` weight, or a floor on `gamma`
(currently unconstrained — the optimizer is free to push it toward zero,
which weakens the Tait equation-of-state pressure response), if uniform
spacing matters more than it currently does.

### Track B — In the loop with Gazebo/Crazyswarm2 (real ROS2 nodes)

Files: `plain_sph.py`, `particle.py`, `potential.py`, `commander.py` (this is
the working path); separately, `controller.py`, `sph_logger.py` (diagnostics
path — currently broken, see Known issue #6).

**`plain_sph.py` is the node that actually flies the drones.** One instance
per drone (via `plain_sph.launch.py`), each subscribed to every `/cf_N/state`
topic, each advancing its own SPH particle one step per control tick (0.05 s)
using the real measured positions/velocities of all currently-known drones.
Each tick it adds an **external force from the potential** to the SPH
acceleration, integrates the particle, and sends the resulting velocity.

**Which constants it flies with (changed since the older version of this doc).**
`plain_sph.py` now imports the configurable `particle.py` (not
`plain_particle.py`), and its defaults are **hand-tuned values, not the CMA-ES
result**: `h=3.0`, `mass=7000`, `rho_0=1000`, `gamma=7`, `alpha=1`, `beta=2`,
`zetta_extra=30`. So the 3-hour CMA-ES search currently has no effect on real
flights. To fly the CMA-ES values, pass them as launch args (they were tuned
with `h=0.75` and `mass=795.2156`, so those go together):
```bash
ros2 launch drone_controller plain_sph.launch.py total_robots:=3 \
  smoothing_h:=0.75 particle_mass:=795.2156 \
  gamma:=0.0457 alpha:=0.6419 beta:=-0.2906 zetta_extra:=0.2905
```
This combination has **not** been flown together with the potential. The
offline tuning had no external force, so expect to re-tune. `plain_particle.py`
is no longer imported by anything on the flight path, and its hardcoded
constants no longer match the CMA-ES values either (it currently has `h=1.0`,
viscosity `[1.0, 2.0]`, damping `5`).

**The potential (`potential.py`).** A circular target: `s = |p - c|²/R² - 1`,
`φ = s²`, and the force on a drone is `-k · ∇φ / |∇φ|^β` — with the default
`β=1` that is a force of constant magnitude `k` pointing toward the circle, so
`|F_ext| ≤ 2` at the defaults. Parameters: centre `(xc, yc)`, radius `R`,
gain `f_k`, exponent `f_beta`. Nothing in it is 3D.

**Control path.** The node calls `Commander.send_velocity_world`, a raw
velocity command (clipped to `max_velocity=0.5` m/s) with no position tracking
— the firmware's own loop handles the rest. Commanding `vz=0` means "no
vertical motion right now", which is not the same as holding a fixed altitude.
The older `send_velocity` call (which used `fixed_z`) is commented out, so the
`fixed_z` parameter / `FIXED_Z` setting is currently read but **unused** by the
control path.

**`plain_sph.launch.py` launch args** (defaults equal the defaults declared in
`plain_sph.py`, so launching with none behaves like a plain launch):

| Arg | Default | Arg | Default |
|---|---|---|---|
| `total_robots` | `2` | `alpha` | `1.0` |
| `robot_prefix` | `cf_` | `beta` | `2.0` |
| `fixed_z` | `0.5` | `zetta_extra` | `30.0` |
| `particle_mass` | `7000.0` | `xc`, `yc` | `2.0`, `2.0` |
| `smoothing_h` | `3.0` | `R` | `0.5` |
| `rho_0` | `1000.0` | `f_k` | `2.0` |
| `gamma` | `7.0` | `f_beta` | `1.0` |

**`controller.py` is a separate, read-only diagnostics node** (subscribes to
state, never publishes any command) meant to log SPH-computed
density/pressure/acceleration as pure telemetry, using `particle.py` and
writing through `sph_logger.py` to `logs/sph_cf_*.csv`.
**It currently does not run — see Known issue #6.**

## How to generate history data

Two independent paths, depending on which track you're working in.

**From a real (simulated) flight — CSV + PNG via `plain_sph`:**
1. Start Gazebo/SITL and Crazyswarm2, either with `./dev_tmux.sh up` or by hand
   (terminals 1 and 2).
2. Launch the SPH controller (included in `up`, or terminal 3 by hand):
   ```bash
   ros2 launch drone_controller plain_sph.launch.py total_robots:=3
   ```
3. Let it fly for as long as you want data, then stop with **Ctrl+C** —
   `plain_sph.py`'s `destroy_node()` flushes and closes the CSV cleanly on
   shutdown, so a clean interrupt is enough; no need for `kill -9`. (`Ctrl+b K`
   / `./dev_tmux.sh stop` does this for you.)
4. CSVs land at `src/logs/plain_sph_cf_<id>.csv` — columns: `t, rho, pressure,
   ext_force_x, ext_force_y, vel_x, vel_y, x, y` (`x`/`y` are the measured
   position; older logs without them are skipped for the position plot).
   Bind-mounted, so they're visible on the **host** immediately.
5. **On the host**, fix ownership before touching the logs — the container
   writes these as `root`, so your host user can't read or overwrite them
   yet (see Known issue #8). `./dev_tmux.sh stop` already does this; after a
   manual run:
   ```bash
   sudo chown -R $USER:$USER ~/SPH_Project/src/logs
   ```
6. Generate the plots (works on the host too — only needs `numpy` and
   `matplotlib`, not ROS):
   ```bash
   cd ~/SPH_Project/src
   python3 plot_plain_sph.py
   ```
   Saves two images in `src/logs/` and opens both in your default viewer:
   - `plain_sph_metrics.png` — density, pressure, |external force| and
     |velocity| over time, one line per drone.
   - `plain_sph_potential.png` — **the trajectory plot**: the potential field
     with the target circle and each drone's path (left; circle = start,
     square = end), and distance to the circle centre vs. time (right).

   `plain_sph_trajectory.png` in older checkouts comes from an earlier version
   of the script and is no longer generated.

   **The plot script hardcodes the circle** (`XC = 2.0`, `YC = 2.0`, `R = 0.5`
   at the top of `plot_plain_sph.py`) and does not read `swarm.conf`. If you
   changed `POT_XC`/`POT_YC`/`POT_R` for a run, edit those three lines to
   match or the plotted circle will be wrong.

Re-running `plain_sph.launch.py` **overwrites** the same CSVs (`'w'` mode,
not append) — copy old ones elsewhere first if you want to keep a specific
run for comparison. Conversely, **CSVs from drones that no longer exist are
not deleted**: after a 5-drone run followed by a 3-drone run,
`plain_sph_cf_3.csv` and `plain_sph_cf_4.csv` are still there and
`plot_plain_sph.py` will plot them (it globs every `plain_sph_*.csv`). Delete
the extras before plotting.

**From an offline simulation — no Gazebo needed, seconds instead of a full flight test:**
```bash
cd src/drone_controller/drone_controller
python3 raw_sim.py --gamma <g> --alpha <a> --beta <b> --zetta_extra <z> --headless
```
Calls `sim.plot_history()` automatically at the end (density, pressure,
min/max velocity over time). Use this first when trying a new parameter set
— it's what `CMA_ES.py` itself uses internally to score every candidate, so
if something looks wrong here, the full ROS/Gazebo flight will show the same
problem, just much slower to discover. (It has no external potential, so it
cannot reproduce the ring behaviour.)

## Known issues / deliberate workarounds

### 1. colcon misidentifies `drone_controller` as `(python)`, not `(ament_python)`
- **Symptom:** `ros2 run` / `ros2 launch` fail with "Package not found" or
  "No executable found" even after a clean `colcon build`.
- **Root cause:** not fully resolved. Installing `python3-catkin-pkg` (already
  added to `docker/sim.Dockerfile`) was a reasonable hypothesis from reading
  `colcon-ros` source, but it did **not** fix the misclassification. Left open
  for a future revisit — not currently blocking.
- **Workaround:** `src/dev_setup.bash` manually does what the `ament_python`
  build task would have done automatically:
  - adds `/root/dev_ws/install/drone_controller` to `AMENT_PREFIX_PATH`
  - symlinks the plain-Python `bin/<exe>` into `lib/drone_controller/<exe>`,
    which is where `ros2 run`/`ros2 launch` actually look.
- **Rule:** always `source src/dev_setup.bash`. Every new `console_scripts`
  entry added to `setup.py` needs one more symlink line added there too
  (currently covers `hello_node`, `controller`, `plain_sph`).

### 2. The high-level commander (takeoff/land/goto) never stands down on its own
- Confirmed by direct test: streaming `cmd_full_state` only "wins" by arriving
  more recently than the high-level commander's own internal setpoint — it
  does not disable it.
- **Proof:** stopping a controller node mid-flight causes an instant snap-back
  toward wherever `takeoff` originally left the drone, not a stay-put.
- `notify_setpoints_stop` exists to hand off control explicitly — **not yet
  confirmed** whether it durably prevents the snap-back or just delays it.
- **Practical rule:** a controller must never stop publishing while it's
  actually flying the drone. Right now, a crash/exception/Ctrl+C means an
  uncontrolled instant setpoint jump, not a safe stop. No watchdog/safe-hold
  behavior exists yet.
- This was established for the full-state streaming path. It has not been
  re-checked for `send_velocity_world`, which `plain_sph.py` uses now.

### 3. Commander API has moved on again since this note was first written
- `commander.py` no longer has `send_hold` or `send_goal`. Current API:
  - `send_velocity_world` — raw velocity command, no position tracking
    (**what `plain_sph.py` uses now**);
  - `send_velocity` — closed-loop from a *desired velocity*: integrates a
    self-consistent position/velocity/acceleration triple, clamped by
    `max_velocity`/`max_acceleration` (what `hello_node.py` uses, with
    `v_des = KP * (target - position)`);
  - `send_accel` — same idea from a *desired acceleration*;
  - the stateless `send_state` underneath the last two.
  See the docstring at the top of `commander.py`.
- The original problem this section described (a fixed-step command with
  `v=0, a=0` regardless of actual distance, which crashed two drones under
  load) is moot with the current API — there's no fixed-step "hold" method
  left to misuse. Kept here for history.

### 4. Host vs. container terminal mix-ups
- This host has its own ROS2 (Jazzy) and Docker install, separate from
  everything above. Running `ros2`/`colcon` directly on the host produces
  confusing, unrelated errors (wrong `install/`, `Permission denied` under
  `/root`, "Package not found" for a *different* reason than issue #1).
- Always check the prompt before running anything. (The tmux launcher avoids
  this: everything goes through `docker compose exec`.)

### 5. Recovering from a drone crash
- After any hard crash (drone hits the ground hard, or `/cf_x/state` starts
  reporting non-physical values — huge velocities, all-zeros, etc.), fully
  restart Gazebo/SITL and Crazyswarm2 before trying anything else
  (`./dev_tmux.sh stop` then `up`). Don't re-takeoff on top of a corrupted
  physics state.

### 6. `controller.py` currently crashes on startup
- **Symptom:** `TypeError` in `Controller.__init__`, or shortly after in
  `_monitor_step` if construction is patched around.
- **Root cause:** written against a different, richer `Particle` interface
  than the one `particle.py` currently exposes:
  - calls `Particle(..., z=0.0, ...)` — current `Particle.__init__` is 2D
    only, no `z` parameter.
  - calls `p.set_rho(...)` / `p.set_pressure(...)` — current class sets these
    via plain attribute assignment (`p.rho = ...`, `p.P = ...`); no setter
    methods exist.
  - calls `ego_particle.next_vel(neighbor_particles, neighbor_data)` —
    current `next_vel(self, q_list)` takes exactly one argument.
- **Not yet fixed.** Either update `controller.py` to match the current 2D
  `particle.py` (drop `z`, use attribute assignment, drop the second
  `next_vel` argument), or extend `particle.py` with the 3D/setter interface
  `controller.py` expects — depends which direction the diagnostics track is
  meant to go. **`plain_sph.py` is unaffected** — it uses `particle.py`
  through the interface that does exist.

### 7. `sitl_multiagent_text.sh` (GUI) needs `xhost` on the host first
- The GUI variant of the launch script (`_text.sh`, vs. the default
  `_headless.sh` used in Terminal 1 above) spawns Gazebo's separate GUI
  process (`gz sim -g`), which needs to connect to the host's X server.
- **Symptom if skipped:** physics/firmware start fine (drones spawn,
  handshake succeeds), but the GUI process crashes with `qt.qpa.xcb: could
  not connect to display` / `Authorization required, but no authorization
  protocol specified`, and the script aborts right after.
- **Fix:** on the **host** (not in the container), once per login:
  ```bash
  xhost +local:root
  ```
  `docker-compose.yaml` already mounts `/tmp/.X11-unix` and forwards
  `$DISPLAY` — the missing piece is always the host-side X authorization,
  never the container config. (`dev_tmux.sh up` runs this for you.)
- **Default recommendation:** just use `_headless.sh` unless you specifically
  need to watch the simulation live.

### 8. `logs/*.csv` and `*.png` come out owned by `root`
- **Symptom:** `python3 plot_plain_sph.py` on the host fails with
  `PermissionError: [Errno 13] Permission denied` when it tries to
  `savefig` into `src/logs/`.
- **Root cause:** `plain_sph.py` (and `controller.py`) run as `root` inside
  the container. `src/logs/` is bind-mounted, so the files it writes are
  owned by `root` on the host too — your normal host user has no write
  access to that directory or its existing files.
- **Fix:** `./dev_tmux.sh stop` / `Ctrl+b K` does it automatically (inside the
  container, as root, no `sudo` prompt). After a manual run, on the host:
  ```bash
  sudo chown -R $USER:$USER ~/SPH_Project/src/logs
  ```
- This isn't a one-time fix — every fresh run of `plain_sph.launch.py`
  re-creates the CSVs as `root` again.

### 9. Container doesn't come back on its own after a PC restart
- **Symptom:** `docker compose exec -it crazysim bash` immediately says
  `service "crazysim" is not running` — no container, no error from Docker
  itself, just a plain refusal.
- **Root cause:** `docker-compose.yaml` has no `restart:` policy set, so the
  container is not brought back up automatically on boot/Docker daemon
  restart. This has nothing to do with the image or the build — it's simply
  not running yet.
- **Fix, every session after a reboot, before anything else:**
  ```bash
  cd ~/SPH_Project
  docker compose up -d crazysim
  ```
  Then `docker compose exec -it crazysim bash` works as normal.
  `./dev_tmux.sh up` does this for you.
- **If `up -d` itself fails or the container exits immediately**, that's a
  different problem — check `docker compose ps -a` (look for `Exited`) and
  `docker compose logs crazysim` for the actual error before assuming it's
  this issue.

### 10. `ros2: command not found` when running commands non-interactively
- **Symptom:** a command run as `docker compose exec crazysim bash -lc '...'`
  builds fine (`colcon` is installed system-wide) but then fails with
  `ros2: command not found`.
- **Root cause:** ROS is sourced from `/root/.bashrc` (added by the
  Dockerfile). `bash -lc` is a login but **non-interactive** shell and never
  reads `.bashrc`. An interactive `docker compose exec -it crazysim bash` does,
  which is why the manual procedure never hit this.
- **Fix (already in `dev_tmux.sh`):** every non-interactive command sources
  `/opt/ros/humble/setup.bash` and
  `/CrazySim/crazyswarm2_ws/install/setup.bash` explicitly first. Do the same in
  any script you add.

### 11. `config/` files must be rewritten in place
- `agents.txt` and `crazyflies.yaml` are single-file bind mounts. A tool that
  writes a temp file and renames it replaces the inode, and the container keeps
  seeing the old file. `gen_config.py` truncates and rewrites in place on
  purpose — don't change that.

### 12. `pkill -f` inside `bash -lc` kills its own shell
- A plain `pkill -f plain_sph` in `docker compose exec crazysim bash -lc '...'`
  matches the `bash -lc` command line itself, kills it, and the rest of the
  chain never runs. `dev_tmux.sh stop` uses the `[x]` pattern trick
  (`pkill -f '[p]lain_sph'`) to avoid this.

## Multi-drone config

Two files must stay in sync, same order, same count:
- `config/crazyflies.yaml` — robot list, `uri: udp://127.0.0.1:1985<N>`,
  `initial_position`.
- `config/agents.txt` — matching `x, y` spawn list.

`gen_config.py` writes both consistently for N drones (and `dev_tmux.sh up`
runs it for you); editing by hand also works if you keep them matched.

`custom_topics` (not `default_topics`) is what makes `/cf_N/state` exist —
easy to get wrong silently (no error, the topic just never appears).
`gen_config.py` leaves everything except the `robots:` block untouched, so the
existing `crazyflies.yaml` remains the template.
