# Running the SPH controller on real Crazyflies

**Status: written without access to hardware. Nothing below has been flown.** The controller code paths
(wall-clock mode, geofence, hover service) are tested offline; everything about radios, positioning systems and
firmware behaviour is from general Crazyflie/Crazyswarm2 knowledge and is marked **[verify]** where I am not sure.
Start with one drone, props guarded, over soft ground, and expect to adjust.

---

## 0. What is different from the simulation

| | Simulation | Real drones |
|---|---|---|
| clock | Gazebo simulated time (`SIM_CLOCK=gz`) | wall time = physical time (`sim_clock:=wall`, the default). No RTF problem exists |
| positions | exact Gazebo/SITL | your positioning system's estimate (noisy, may jump) |
| link | UDP, lossless | Crazyradio, limited bandwidth: 20 Hz × N drones may not all arrive |
| drone dynamics | SITL model | real velocity-loop lag, battery sag, downwash between close drones |
| failures | restart | a drone can fall |
| config | `config/crazyflies.yaml` generated by `gen_config.py` | `config/crazyflies_real.example.yaml`, edited by you |

The SPH loop itself is unchanged: state at 20 Hz in, `v_cmd = v_meas + a·dt` out through `cmd_velocity_world`, clipped at `max_velocity`.

## 1. Hard requirements (without these, do not fly the swarm)

1. **A common world frame for all drones.** SPH uses distances *between* drones, so every drone's `stateEstimate.x/y` must be in the same coordinate frame.
   * Lighthouse (2+ base stations, geometry calibrated and written to the drones), Loco Positioning (LPS) or a mocap system: OK.
   * Flow deck only: **not OK.** Each drone's origin is where it booted, so inter-drone distances are meaningless.
2. **Check the frame with a ruler.** Place two drones 1.00 m apart, run the check in §4 stage 0 and compare `x, y` to the tape measure (±5 cm). The controller ignores `initial_position`; only the estimate counts.
3. **A way to cut power and a safe space**: net or soft floor, no people under the drones, a clear 1.5 m margin around the fence, and someone whose only job is the emergency command.
4. **The safety latch on** (§3), tested with a drone on the ground before the first flight.

## 2. Files you need

* `config/crazyflies_real.example.yaml` → your real drone config (URIs, positions, type). **`./dev_tmux.sh up` overwrites `config/crazyflies.yaml` for the simulator,** so keep the real one under its own name and copy it over only for real flights.
* `src/drone_controller/...`: the same package. It builds on the same machine, no change needed.
* A radio per ~4–6 drones **[verify]**; give each drone its own address with `cfclient`.

## 3. Controller settings for real flights

Launch args of `swarm_sph.launch.py`. Everything is passed on the command line, so `swarm.conf` and `dev_tmux.sh` (which start the simulator) are not used. **The launch file's own SPH defaults (`particle_mass` 3000, `gamma` 1, `zetta_extra` 50) differ from `swarm.conf` (7000, 2, 10): pass the values you want explicitly, as below.**

| arg | value for real drones | why |
|---|---|---|
| `platform` | `real` | labels the run; the analyzer then reads the state rate as link quality instead of guessing a simulator speed |
| `sim_clock` | `wall` | physical time |
| `max_velocity` | `0.2` first, later 0.3–0.5 | the command is clipped here |
| `start_gate` | `flight` | commands zero until every drone is above 80 % of `fixed_z` for 1 s |
| `stale_policy` | `hold` first (try `predict` later) | on a radio link a missed message should not make the model extrapolate |
| `fence_xmin/xmax/ymin/ymax` | room limits **minus a margin**, in the positioning frame | a drone outside the box, or an estimate that jumps out, latches 0 m/s for the whole swarm |
| `state_timeout_s` | `1.0` | no state from any drone for 1 s latches 0 m/s |
| `sph_gain` | `0.25 → 0.5 → 1.0` over successive flights | see stages 3–4 |
| `f_k` | `0` | no external potential at first (it pulls toward `xc, yc` in the world frame) |
| `test_profile` | `zero` / `step` for stages 1–2 | known commands, no SPH |

**What the latch does and does not do.** After a trip (or after `ros2 service call /swarm_sph/hover std_srvs/srv/Trigger`) the controller keeps streaming **0 m/s** to every drone, so the firmware keeps hovering on its own loop. It does **not** land or stop anything. The trip is latched until you restart the node. The event `SAFETY_TRIP` is written to `events.log` with the reason.

**What it cannot protect against:** a crashed or killed controller process, a dead ROS network, a dead radio. Those are firmware-watchdog cases: when setpoints stop, the Crazyflie commander eventually levels and then cuts the motors (I recall about 0.5 s and 2 s **[verify in the firmware version you flash]**). So never `Ctrl+C` the controller while drones are in the air, use the hover service first (§5).

## 4. Bring-up, in order. Do not skip a stage.

Terminal A (Crazyswarm2, real config):

```bash
ros2 launch crazyflie launch.py backend:=cflib rviz:=False
```

Terminal B (controller, example for 3 drones; adapt the fence to your room):

```bash
cd /root/dev_ws && source src/dev_setup.bash      # same as in the simulation workflow
ros2 launch drone_controller swarm_sph.launch.py total_robots:=3 \
    platform:=real sim_clock:=wall max_velocity:=0.2 start_gate:=flight stale_policy:=hold \
    fence_xmin:=-1.5 fence_xmax:=1.5 fence_ymin:=-1.5 fence_ymax:=1.5 state_timeout_s:=1.0 \
    particle_mass:=7000.0 gamma:=2.0 zetta_extra:=10.0 smoothing_h:=3.0 rho_0:=1000.0 \
    f_k:=0.0 run_label:=real_s0
```

### Stage 0 — bench, props OFF (or drones in your hand)

1. Terminal A up, drones connected. `ros2 topic hz /cf_0/state` should be close to 20 Hz for every drone at the same time. If one is much lower, reduce `firmware_logging.custom_topics.state.frequency` to 10 or add a radio.
2. `ros2 topic echo /cf_0/state --once` for each drone while standing at known tape-measured spots: x, y, z must match within a few cm and share one frame (§1 item 2).
3. Start the controller with `sph_gain:=0.0 test_profile:=zero`. Open `events.log`: `FIRST_RX` for every drone, no `SIMCLOCK_*` lines.
4. **Test the latch**: carry one drone past the fence by hand, `events.log` must show `SAFETY_TRIP` and the commands must be 0. Also try `ros2 service call /swarm_sph/hover std_srvs/srv/Trigger`. Stop the node.

### Stage 1 — one drone hovers (`total_robots:=1 test_profile:=zero`)

1. Take off with the Crazyswarm2 service (the same call `dev_tmux.sh` makes in the simulation):
   `ros2 service call /all/takeoff crazyflie_interfaces/srv/Takeoff "{height: 0.5, duration: {sec: 3, nanosec: 0}}"`
2. Wait until it hovers steadily, then start the controller (`test_profile:=zero start_gate:=flight`). It streams 0 m/s.
3. 30 s of hover, then land (§5). Analyze: `python3 src/analyze_run.py <run folder>`.
   * **Pass:** C6 (own drift) small (the simulation showed 1 mm/s; a few cm/s on hardware is typical **[verify]**), C14 altitude hold within ±5 cm, C1 state rate ≥ 17 Hz.
   * If the drone drifts at 0 m/s command, fix that first (positioning calibration, battery, props). The SPH controller cannot fix an estimator problem.

### Stage 2 — measure the real drone (step response)

Same as stage 1 with `test_profile:=step test_amp:=0.1 test_period:=4`. The analyzer's **C5** gives the real velocity gain and lag.
Compare with the simulation (T3a). If the real lag is larger than about 0.2–0.3 s, or the gain is far from 1, the SPH gains tuned in simulation may be unstable on hardware. Reduce `sph_gain`, or raise `zetta_extra`, before stage 3. This stage is what tells you whether the simulation result transfers at all.

### Stage 3 — two or three drones, SPH on, low gain

Place the drones on the ring that the SPH density predicts (equilibrium, so nothing should move much):

```bash
python3 gen_config.py --n 3 --print-radius --mass 7000 --h 3 --rho0 1000     # -> 0.445 m radius (0.77 m spacing)
```

(use your own `particle_mass`, `smoothing_h`, `rho_0`; keep spacing ≥ 0.5 m because of downwash **[verify]**).
Launch with `sph_gain:=0.25`, takeoff, start the controller, watch 30–60 s, land. Analyze. Then `0.5`, then `1.0`, each as a new flight.

**Go/no-go for the next gain:** C7 (oscillation) shows `none/steady`, C9 (closest approach) well above 0.4 m, C12 (saturation) near 0 %, no `SAFETY_TRIP`. If C7 says GROWING, stop: that is a stability problem of the loop with *this* drone's lag, not a bug.

### Stage 4 — more drones, external potential

Add drones one at a time (radio load, `ros2 topic hz`). Only after the free swarm is calm switch `f_k` on (and set `xc yc R` to world coordinates in the positioning frame, `fence_*` large enough for the circle).

## 5. Stopping and landing — the part that must be right

Land **with the controller still running**:

1. `ros2 service call /swarm_sph/hover std_srvs/srv/Trigger` → drones hover on firmware loops, setpoints keep streaming.
2. Hand control back to the high-level commander, then land. In recent Crazyswarm2 versions there is a "notify setpoints stop" service for this; **[verify]** with `ros2 service list | grep -i notify` and `ros2 interface show crazyflie_interfaces/srv/NotifySetpointsStop`. Typical call: `ros2 service call /all/notify_setpoints_stop crazyflie_interfaces/srv/NotifySetpointsStop "{group_mask: 0, remain_valid_millisecs: 100}"`
3. `ros2 service call /all/land crazyflie_interfaces/srv/Land "{height: 0.0, duration: {sec: 4, nanosec: 0}}"`
4. Only when all drones are on the ground, `Ctrl+C` the controller.

**Practice this on one drone at 0.5 m** before any multi-drone flight. Emergency stop: Crazyswarm2's `emergency` service (`ros2 service list | grep emergency`) **cuts the motors, the drones fall.** Know the command before you need it.

## 6. After the flight

```bash
python3 src/analyze_run.py src/logs/runs/<run folder>        # the same one-page verdict as in simulation
python3 src/analyze_run.py --compare <sim run> <real run>    # side by side
```

`platform=real` runs show C1 as the state-stream rate. If it is under 17 Hz, delay in the loop is higher than in simulation, and `STALE-STATE` will say how many ticks had no new message. The logs, columns and events are identical to the simulation, so everything in TEST_GUIDE.md about reading them still applies (T3 = stage 2, T4 = stage 3).

## 7. Things I could not check (please tell me what you find)

* The exact firmware watchdog timeouts and the behaviour of velocity-world setpoints when they stop.
* The name and fields of the notify-setpoints-stop service in your Crazyswarm2 version.
* `tracking: "off"` in the example config for Lighthouse/LPS in the `fileversion: 3` format.
* Whether `vz = 0` holds altitude on your estimator. It commands zero climb rate; it is not an altitude hold (the analyzer's C14 shows what happens).
* Radio capacity: how many drones' 20 Hz `state` streams one Crazyradio carries.
* How the SPH loop behaves with real drone lag: that is what stages 2–3 measure.
